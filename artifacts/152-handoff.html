A　認識系統

1系統總覽

這套系統要達成三件事：（1）不被外部隨意攻擊，資料不被偷；（2）Gitea 與 pyDMS 只給校內使用，而且校內也走 HTTPS；（3）切斷外部存取。做法是單一入口、多層 IP 圍籬、後端只聽本機。

nginx 的處理階段：為什麼 80 的 allow/deny 無效

nginx 處理一個請求時分成固定的階段，順序與設定檔裡的書寫順序無關。return 與 rewrite 屬於 rewrite 階段，allow／deny 屬於 access 階段，而 rewrite 階段比較早。

  • 80 的 server 區塊裡有 return 301，所以請求在 rewrite 階段就被回覆了，輪不到 allow/deny。
  • 443 的 server 區塊沒有 return，allow/deny 正常執行。
  • 證據（access.log，2026-08-21 13:27:15）：不在白名單的 127.0.0.1 打 80 得到 301，打 443 得到 403。
  • 結論：80 的存取控制目前只靠防火牆。而防火牆沒有 80 的規則，所以 80 現在對所有人都是擋下的。新增 80 規則時，來源一定要限定校內網段。

當初卡最久的九個觀念

  • 防火牆管「這個來源能不能敲到這個 port」；port 有沒有人聽是另一回事。兩者都要成立才連得上。逾時＝防火牆丟掉；拒絕＝沒人聽。
  • nginx 沒有特權，它只是另一個行程。它能「管」後端，是因為後端故意只聽 127.0.0.1，外面只剩 nginx 這一扇門。
  • 127.0.0.1 永遠指「自己這台」。在別台機器上打 127.0.0.1 測不到 152。
  • 瀏覽器連別人的 80/443 時，自己這端用的是隨機高位 port。防火牆規則裡的 port 永遠是「我這台要開給別人的門」。
  • Gitea 和 pyDMS 一輩子只講 HTTP；https 是 nginx 一個人的事。對 3000/8000 做 https 必失敗。
  • 兩個後端的 proxy_pass 結尾一個不加斜線（pyDMS，自己認前綴）、一個要加（Gitea，nginx 剝前綴）。Gitea 的加斜線寫法會解碼 %2F，並非官方做法，改版見nginx 改版。
  • nginx 處理請求分階段：rewrite 階段（return、rewrite）早於 access 階段（allow／deny）。所以同一個區塊裡先寫 allow/deny、再寫 return，return 還是先執行。
  • 只有 C:\nginx\conf\nginx.conf 會生效。改完要 -t 再 -s reload。
  • 服務被 NSSM 自動重啟時 PID 會換。看到「關了還在」先查 AppExit，不要懷疑靈異。

  4. 用工作排程器定期執行，並保留多份。
  5. 做一次還原演練，確認備份真的能用。

做法與指令見 8.7。

4設計決策與取捨

每一條都照「決策／替代方案／為什麼這樣選／代價」寫。日後想改架構時，先看當初放棄了什麼、換來了什麼。

單一入口：外面只看得到 nginx

決策
對外只開 80/443，全部經過 nginx，再依路徑分給 Gitea 與 pyDMS。
替代方案
每個服務各自對外開 port（以前的 3000、8000 就是這樣）。
為什麼
憑證、白名單、存取紀錄都集中在一處；要守的門只剩一扇。
代價
nginx 停了兩個服務一起斷；nginx.conf 改錯一處兩邊都受影響。

後端只綁 127.0.0.1

決策
Gitea（HTTP_ADDR）與 pyDMS（NDMS_HOST）只聽本機迴路。
替代方案
綁 0.0.0.0，靠防火牆擋外部。
為什麼
就算防火牆規則被誤刪，外面也連不到 3000/8000。這也是 NDMS_TRUST_PROXY=1 安全的前提：只有 nginx 能送標頭進來。
代價
除錯時不能從別台直接打後端；在 152 上直接打也要帶前綴，否則 404 或「Frontend is not initialized」。

TLS 只在 nginx 終結

決策
只有 nginx 持有憑證；nginx 到後端走純 HTTP。
替代方案
Gitea、pyDMS 各自設定 https。
為什麼
憑證只放一份、換一處；後端設定簡單，不用各自處理 TLS。
代價
後端要靠 X-Forwarded-Proto 才知道使用者原本用 https；對 3000/8000 做 https 一定失敗，常被誤判成故障。

三道 IP 圍籬

決策
Windows 防火牆 → nginx allow/deny → pyDMS ip_guard，三層各自檢查來源 IP。
替代方案
只靠防火牆一道。
為什麼
任何一道設錯，後面還有一道接住。Gitea 只有前兩道。
代價
網段清單要在防火牆規則、nginx.conf、pyDMS（.env 或 var/security.json）三處同步；漏改一處就會出現「防火牆放行、nginx 卻擋」這類難追的狀況。80 埠實際上只有第一道（見最後一條）。

用路徑前綴分服務，而不是不同 port

決策
/gitea/、/pydms/ 共用 443。
替代方案
每個服務一個 https port（例如各開一個 port 給 nginx 監聽）。
為什麼
防火牆只要管 80/443；使用者只要記一個網址。
代價
兩個後端都得知道自己的前綴（ROOT_URL、NDMS_URL_PREFIX），nginx 轉發方式也得跟著配合（下一條）。

兩個 proxy_pass 的斜線剛好相反

決策
pyDMS：proxy_pass http://127.0.0.1:8000;（結尾不加斜線），完整路徑原樣轉發，由 pyDMS 自己認 /pydms 前綴。Gitea 現行：proxy_pass http://127.0.0.1:3000/;（結尾加斜線），由 nginx 剝掉 /gitea/。
替代方案
Gitea 改用官方子路徑寫法：rewrite ^ $request_uri; 取回未轉義的原始 URI，再剝前綴後以 $uri 轉發（nginx 改版）。
為什麼
現行寫法是當初能讓 Gitea 子路徑正常運作的最短設定。它不是官方標準做法，之前文件寫錯了。
代價
結尾斜線寫法會把網址裡的 %2F 解碼，含 %2F 的 Gitea 網址可能被轉錯；改版前後兩個 location 的寫法都不一樣，是最容易改錯的地方。

自簽憑證

決策
用 openssl 自簽，CN 與 SAN 都是 IP，效期 10 年。
替代方案
向計中申請正式憑證，或申請網域名稱後用 Let's Encrypt。
為什麼
這台只有 IP、沒有網域，自簽立即可用。
代價
瀏覽器每次都警告；git 要對該 repo 設 http.sslVerify false。

git 對自簽憑證：關閉驗證（false）或信任憑證（true） 待決定

當初的決策
對每個要連 152 的倉庫各自執行 git config --local http.sslVerify false，範圍只限單一倉庫，不加 --global。
為什麼當初這樣選
152 的憑證是自簽的、只有 IP 沒有網域，而且 Git Credential Manager 的 OAuth 在 Gitea 子路徑下失敗，所以先用 Personal Access Token 加關閉驗證，最快讓 clone、push 能用。
關閉驗證（false）實際代表什麼
連線仍然加密，但 git 不再確認對方真的是 152。若有人在路徑中間假冒伺服器，git 不會發現，token 也可能被拿走。在校內白名單網段內機率低，但不是零。
替代方案
（C）讓每台電腦信任 152 的 server.crt，驗證保持開啟；（D）向計中申請正式憑證，或申請網域名稱，這是最徹底的做法，所有人與瀏覽器都不用再設定。
代價
C 需要每台電腦各做一次，憑證更換後要重做。D 需要網域或計中配合。目前沒有任何一台電腦實際驗證過 C。
2026-11-25 補充
PL-1125-GIT-1：本專案所有要跟 Gitea 更新的地方，一律先照常 pull；失敗而且原因是憑證錯誤，才只對那個 repo 補 git config --local http.sslVerify false 再試一次。pyDMS 自己跑 git 的三個地方都照這條做，不動 --global 設定。這條統一的是現行做法；要不要改成信任憑證，仍未決定。
建議
短期維持 --local 的 false；先在一台電腦驗證 C，確認可行後再推廣。哪一種由管理者決定。

NSSM AppExit = Restart，實驗時暫改 Exit

決策
nginx 與 python-dms 由 NSSM 管，程式結束就自動重啟。
替代方案
Exit：程式結束就停著，等人處理。
為什麼
正式運作時當掉能自己恢復，不用有人守著。
代價
做「關掉看看」的實驗會被救活，要先暫改 Exit、做完改回；install_services.bat 重建服務會把它重設回 Restart。Gitea 不歸 NSSM 管；8 月查詢 sc.exe qfailure gitea 時沒有任何失敗動作，當掉不會自動重啟。

80 埠目前只靠防火牆 待決定

決策
現況：80 的 server 區塊只做 return 301，存取控制只靠 Windows 防火牆規則（該規則尚未新增，所以 80 目前全擋）。
替代方案
候選做法：改用 try_files 搭配具名 location，在具名 location 裡才 return 301，讓 allow/deny 先執行。尚未在 152 驗證。
為什麼
nginx 的 return 在 rewrite 階段執行，早於 access 階段的 allow/deny，所以 80 區塊裡那幾行 allow/deny 從來沒有作用。證據：access.log 中不在白名單的 127.0.0.1 打 80 拿到 301、打 443 拿到 403。
代價
80 只有一道圍籬；防火牆規則一旦放寬，任何人都能拿到 301 轉址（只有轉址，沒有內容）。

Gitea 用 sc.exe 註冊成服務，不用 NSSM

決策
install_services.bat 先試 gitea.exe manager service install，失敗後改用 sc create gitea。152 上實際走的是後者。
替代方案
和另外兩個服務一樣交給 NSSM 管。
為什麼
Gitea 1.27.0 沒有 manager service 這個子指令（回 No help topic for 'service'），腳本的備援路徑就是 sc.exe。
代價
沒有 NSSM 的自動重啟與 stdout 落檔；服務帳號是 LocalSystem，與 app.ini 的 RUN_USER = Administrator 不一致，影響未知；8 月查詢時沒有設定任何失敗動作。

git 認證用 Personal Access Token，不用瀏覽器 OAuth

決策
clone／push 一律用 PAT。
替代方案
讓 Git Credential Manager 跳瀏覽器走 OAuth。
為什麼
GCM 的 OAuth 在 Gitea 子路徑下會失敗：授權網址少了 /gitea 前綴得到 404，或導回 127.0.0.1:<隨機 port> 時 connection refused。
代價
每個人要自己產生並保管 token；token 過期或撤銷後要重設。

Gitea 資料庫用 SQLite

決策
DB_TYPE = sqlite3，資料庫是單一檔案 C:\gitea\data\gitea.db。
替代方案
MySQL 或 PostgreSQL。
為什麼
當初選擇的原因 待補。
代價
備份時要先停 Gitea 再複製，否則可能複製到不一致的檔案。好處是備份與搬家只要帶走 C:\gitea\data 整個資料夾。

    目的
    建立 pyDMS 的工作副本與 venv。第 9 步的腳本會檢查 .venv\Scripts\python.exe 存在，所以這步要先做。
    倉庫現況
    2026-11-24 起，pyDMS 的倉庫是 DZLab/pyDMS（舊的 new_ntu_data_management_system 已刪除、重新建立）。本文件其他章節仍有舊名稱，還沒有全文更新 待辦。工作資料夾建議用 C:\pyDMS。
    怎麼選做法
    看 Gitea 與 nginx 有沒有已經在運作。已經在運作（例如這次更換資料夾）用做法一；全新機器上 Gitea 還沒起來，用做法二。

    做法一：Gitea 與 nginx 已在運作（https）

    • -c http.sslVerify=false：只在這一次 clone 跳過憑證驗證。原因是 152 的憑證是自簽的，Windows 不信任它，會出現 schannel: SEC_E_UNTRUSTED_ROOT（見 FAQ）。clone 完成前還沒有 repo 可以設定，所以要用 -c。

    • -c credential.helper=：這次不使用 Windows 的 Credential Manager，改由終端機直接詢問帳號與密碼；密碼欄貼上 Personal Access Token（輸入時不會顯示字元）。為什麼不用 Credential Manager：它在 Gitea 子路徑下會跳瀏覽器走 OAuth 然後 404（9.2）。完整的認證設定見 9.2.1。

  1. 新機先備妥，不碰舊機。做第 5 章的第 2、3 步（不含還原資料）：設定網路、安裝軟體、建目錄。

9.2　用 Personal Access Token 做 clone 與 push

git 連 Gitea 時不要用帳號密碼的瀏覽器登入流程，改用 Personal Access Token（PAT）。原因：Windows 的 Git Credential Manager 會嘗試開瀏覽器走 OAuth，但它不知道 Gitea 掛在 /gitea/ 底下，結果是 404，或導回 127.0.0.1:某個 port 時連線被拒。

  1. 瀏覽器 登入 Gitea → 右上角頭像 →「設定」→「應用程式」→「產生新的 Token」。名稱寫用途（例如「我的筆電」），權限勾 repository 的讀取與寫入。
  2. 產生後畫面上會顯示一串字，只顯示這一次。複製後存到密碼管理工具。它等同你的密碼，不要貼到聊天室、信件或程式碼裡。
  3. clone 時網址裡放帳號，詢問密碼時貼上 token：
  • git -c http.sslVerify=false clone …：-c 只對這一次指令生效。clone 完成前還沒有 repo 可以設定，所以先用這個方式。
  • 網址的格式是 https://主機/gitea/擁有者/倉庫.git。在 Gitea 網頁的倉庫首頁可以直接複製。
  • 已經 clone 好、只是 remote 還指向舊網址的 repo，用 git remote set-url origin <新網址> 修改，不用重新 clone。

9.3　自簽憑證的處理

目前狀態關閉這個 repo 的憑證驗證

  • 簡單，馬上能用。
  • 代價：git 不再確認對方真的是 152。連線仍然有加密，但無法防止有人在中間假冒伺服器。
  • 不要加 --global。那會讓這台電腦上所有 repo、連所有網站都不驗證憑證。

建議目標讓 git 信任這一張憑證 待辦未實施

  • 向管理者拿 server.crt（公開的憑證，可以傳；server.key 是私鑰，絕對不能傳），放在自己電腦上固定的位置。
  • 好處：驗證保持開啟，git 只信任這一張，其他來源一律拒絕。
  • 前提：憑證的 SAN 要包含 IP 待補（系統資訊）。
  • 憑證更換後，每個人都要換新的檔案。

這個做法還沒有人實際用過。Git for Windows 若使用 Windows 內建的 TLS 元件（schannel），http.sslCAInfo 可能不會生效。2026-11-24 實際出現的錯誤 schannel: SEC_E_UNTRUSTED_ROOT 就是 schannel 在用 Windows 的憑證庫驗證，所以比較可能有效的做法是把憑證匯入 Windows 的受信任根憑證（見下一段，同樣尚未驗證）。

2026-11-25 補充（PL-1125-GIT-1）。本專案所有要跟 Gitea 更新的地方，一律先照常 pull；失敗而且原因是憑證錯誤，才只對那個資料夾補 git -C <資料夾> config --local http.sslVerify false 再試一次。pyDMS 自己跑 git 時已經照這條做，不動 --global；有沒有被自動關掉，看管理頁 Git 狀態的「憑證檢查」。

讓這台電腦信任 152 的憑證（Windows，尚未驗證）待辦

  • 只匯入「目前使用者」的受信任根憑證，不需要系統管理員權限；會跳出確認視窗，按「是」。
  • 只能拿 server.crt，server.key 是私鑰，絕對不能離開 152。
  • 匯入後，這台電腦上所有 152 的倉庫，以及 Chrome，都會信任它，不必每個倉庫各自關驗證。
  • 若接著出現 CRYPT_E_NO_REVOCATION_CHECK：自簽憑證沒有撤銷清單可查，可對單一倉庫執行 git config --local http.schannelCheckRevoke false。不建議加 --global，那會讓這台電腦所有 HTTPS 站台都不檢查撤銷。
  • 若出現憑證名稱不符：憑證的 SAN 沒有 IP，要重新產生憑證（5.5）。
  • 憑證更換後（8.8），每台電腦都要重新匯入新的 server.crt。

9.4　不要在 152 的 gitea-repositories 裡改檔案

C:\gitea\data\gitea-repositories\<擁有者>\<倉庫>.git 是 bare repo：只有 git 的內部資料（objects、refs、hooks），沒有工作目錄，所以裡面看不到你的程式檔案，這是正常的。

  • 不要在裡面新增、修改、刪除任何檔案，也不要在裡面執行 git gc、git prune、git commit。這些資料夾由 Gitea 管理，手動改動可能讓 Gitea 的資料庫與倉庫內容對不上，或直接損壞倉庫。
  • 要看內容或改程式：在自己的電腦 clone 出來，改完 push 回去。
  • 管理者需要檢查倉庫時，只用唯讀的指令（git --git-dir=… fsck、log、count-objects）；要做實驗，先 robocopy 到 C:\recovery 在副本上做。
  • 要刪除倉庫：從 Gitea 網頁刪（倉庫 →「設定」→ 最下方的危險區域），不要直接刪資料夾。

9.5　152 上的工作副本：本機路徑與 https 的差異

152 上 C:\New-NTU-Data-Management-System 的 origin 是本機路徑，直接讀 Gitea 的倉庫資料夾。這和大家用的 https 網址是同一個倉庫，但走的路不同：

  • 本機路徑不經過 nginx 與 Gitea，所以不需要 token、不受憑證影響，Gitea 停著也能 pull。相對地，Gitea 的權限與紀錄完全管不到它。
  • 在 152 上只 pull，不要 push。從本機路徑 push 會直接寫入倉庫檔案而不經過 Gitea，Gitea 的網頁與資料庫是否會正確反映沒有確認過。要改程式一律在開發電腦改，經 https push。
  • 完整比較與改用 https 的做法見 5.11。已決定 2026-11-25採用 https 加專用帳號，不採用本機路徑（PL-1125-GIT-2，9.2.1）。這一節描述的是舊資料夾的情況。

代表 443 的防火牆規則來源還是 Any，封包穿過防火牆到了 nginx，被 nginx 的 deny all 擋下。功能上是安全的（看不到內容），但攻擊面沒有收到最小。照 6.6 的收尾指令把 443 規則收緊成校內網段後，校外會變成逾時。

服務明明 stop 了，netstat 還看到 80/443 有人聽

兩種可能：（1）NSSM 的 AppExit=Restart 把它救活了，PID 會變；（2）之前手動雙擊過 nginx.exe，留下一個不受服務管理的行程。查法：Get-CimInstance Win32_Process -Filter "ProcessId=<netstat 看到的 PID>" 看它是誰。前者用 nssm set … AppExit Default Exit 暫時關掉；後者 taskkill /F /IM nginx.exe。

關掉防火牆測試後，外網還是連不到某些 port

先確認那個 port 當下有沒有服務在聽。沒人聽的 port 不管防火牆開關都是 closed，這不是殘留阻擋。用 netstat -ano | findstr LISTENING 對照。測完記得 netsh advfirewall set allprofiles state on。

在 152 上開 https://localhost/… 或 https://127.0.0.1/… 是 403

127.0.0.1 不在 nginx 的 allow 清單裡。在 152 上測試一律用 https://140.112.180.152/…，它落在 140.112.180.0/24 白名單內。若真的需要 localhost，在 443 的 server 區塊加一行 allow 127.0.0.1;，但一般不建議。

同樣是 127.0.0.1，打 http（80）拿到 301，打 https（443）卻是 403

這是 access.log 裡實際看到的現象，也證明了 80 區塊的 allow/deny 沒有作用：nginx 的 return 301 在 rewrite 階段就回應了，輪不到 access 階段的 allow/deny；443 沒有 return，所以 allow/deny 正常執行。80 的存取控制因此只靠 Windows 防火牆。要不要讓 nginx 在 80 也生效 待決定，候選做法見nginx 改版。

用 yougetsignal 之類的外部工具掃，不管怎麼改都是 Closed

那些工具的機房 IP 不在校內網段，被防火牆擋是正確結果。它只能證明「校外連不到」，不能用來驗證校內設定。校內的驗證用機械系電腦。

502 Bad Gateway

nginx 活著，但它要轉發的後端沒有回應。/gitea/ 出現 502 就查 gitea 服務，/pydms/ 出現 502 就查 python-dms：Get-Service gitea, python-dms，再用 netstat 看 3000、8000 有沒有在聽。服務剛重啟的幾秒內出現 502 是正常的。

在 152 上用 127.0.0.1 測不到，換成 140.112.180.152 就可以

nginx 的白名單沒有 127.0.0.1。152 自己的 IP 屬於 140.112.180.0/24，在白名單內，所以用它測才會通過。這是預期行為，不需要修。

HTTPS 與憑證

瀏覽器說「你的連線不安全／不是私人連線」

自簽憑證的正常行為。按「進階」→「繼續前往」。要消掉警告得申請正式憑證（向計中詢問，或用 Let's Encrypt，但那需要一個網域名稱）。

開 443 出現「400 Bad Request — The plain HTTP request was sent to HTTPS port」

你用 http:// 打了 443（例如手打 http://140.112.180.152:443/）。nginx 在 443 只講 TLS，收到明碼 HTTP 就回這句。改打 https://140.112.180.152/（443 是預設，不用寫）。

https://140.112.180.152:3000 或 :8000 是 ERR_SSL_PROTOCOL_ERROR / SEC_E_INVALID_TOKEN

Gitea 和 pyDMS 本身不講 TLS，只有 nginx 有憑證。對 3000/8000 做 https 握手必然失敗。而且現在這兩個 port 只綁 127.0.0.1，從外面根本連不到。走 https://140.112.180.152/gitea/、/pydms/。

通常是憑證警告頁擋在前面，點過去之後看到的是 403 或正常頁面。用無痕視窗、看網址列下方的錯誤代碼原文，而不是憑印象。

pyDMS

https://…/pydms/login 回 401 而不是登入頁

152 上跑的是不支援 URL 前綴的舊版 pyDMS：舊程式只認 /login 是公開路徑，/pydms/login 被當成需要登入。git pull 到支援 NDMS_URL_PREFIX 的版本，重啟 python-dms。

在 152 上直接開 http://127.0.0.1:8000/login 是 404

新版設了 NDMS_URL_PREFIX=/pydms 後，整個站往後挪一層，根目錄會 404。直接打後端要用 http://127.0.0.1:8000/pydms/login；但平常不該直接打後端，走 nginx。

登入列表每個人都是 127.0.0.1

NDMS_TRUST_PROXY 還是 0。站在 nginx 後面所有連線的 TCP 來源都是 nginx 自己（127.0.0.1）。.env 改 NDMS_TRUST_PROXY=1，重啟 python-dms。前提：pyDMS 必須只綁 127.0.0.1（不然任何人塞 X-Forwarded-For 就能冒充）。

登入列表每個人都是同一個校內 IP（像路由器的位址）

兩個可能，先分清楚：（a）大家真的經過同一台做 NAT 的路由器，HTTP 層救不回來，要找路由器的管理者；（b）nginx 的 X-Forwarded-For 是用「附加」寫法，而程式取最左值——這是待辦總表第 4 項的安全修正。先看 nginx access.log 的第一欄（nginx 看到的 $remote_addr）是不是也都一樣，一樣就是 (a)。

上傳大檔後前端噴 JSON.parse SyntaxError

nginx 預設 1MB 上限，超過回一頁 413 的 HTML，前端拿到 HTML 去 parse JSON 就炸。nginx.conf 的 http 區塊要有 client_max_body_size 256m;，改完 nginx -s reload。已完成

改了 .env 沒反應

.env 只在 python-dms 啟動時讀一次，改完要 net stop／net start python-dms。另外 root 在網頁改過的白名單會存在 var/security.json，優先權高於 .env；啟動訊息會印「有網頁覆蓋值」提醒。

用 taskkill 關掉 python.exe 或 nginx.exe，它自己又跑起來

NSSM 的 AppExit Default 是 Restart，程式一結束就會被重新啟動，PID 會換。要讓它停著，用 net stop python-dms（或 nginx）。做實驗需要暫時關掉自動重啟時見 8.9。

Gitea

Gitea 500：getFileReader, packfile not found

pyDMS 頁面跑版（反過來的情況）

pyDMS 的 location /pydms/ { proxy_pass http://127.0.0.1:8000; } 結尾不能有斜線。pyDMS 自己認得 /pydms 前綴，nginx 要原樣轉發。兩個後端剛好相反，是最容易改錯的地方。

到 C:\gitea\data\gitea-repositories 裡找不到我的程式檔案

那是 bare repo，只有 git 的內部資料，沒有工作目錄，看不到檔案是正常的。不要在裡面改任何東西。要看檔案就 clone 出來。見 9.4。

Git

git pull 跳出瀏覽器，然後 404 或 127.0.0.1:某個port 拒絕連線

Windows 的 Git Credential Manager 想用 OAuth 登入 Gitea，但它組網址時不知道 Gitea 在 /gitea/ 子路徑（組成 /login/oauth/authorize，nginx 404），或本機臨時接收埠已逾時。不要走 OAuth，改用 Personal Access Token。

手動操作時（2026-11-25 在 152 上實際成功）：git -c credential.helper= pull --ff-only。這一次不交給 Credential Manager，改在命令列問帳號密碼，密碼欄貼 token（9.2）。把帳號和 token 寫進 remote 網址也能用，但 token 會以明碼留在 .git\config，不建議。

152 server 上：2026-11-25 就遇到這個狀況，關掉憑證檢查之後，git pull 改成跳瀏覽器然後 404（事件紀錄）。長期的做法是在 C:\pyDMS\.env 設 NDMS_GIT_AUTH_USER 與 NDMS_GIT_AUTH_TOKEN（專用帳號與它的唯讀 token）。pyDMS 每次跑 git 自己帶上，不經過 Credential Manager，也就不會跳瀏覽器（9.2.1）。舊資料夾的 remote 是本機路徑，不會碰到這個問題，但這個做法已決定不採用（5.11）。

git clone：schannel: SEC_E_UNTRUSTED_ROOT (0x80090325)　原因已確認
現象（2026-11-24）
機械系電腦 clone DZLab 的 py_Report_Excel、WOS_Report、ESI_Report 都出現同一個錯誤：fatal: unable to access 'https://140.112.180.152/gitea/…': schannel: SEC_E_UNTRUSTED_ROOT (0x80090325)。
原因
Git for Windows 預設用 schannel，也就是 Windows 自己的 TLS 元件，憑證是否可信由 Windows 的受信任根憑證庫決定。152 的憑證是自己簽的，Windows 沒有信任它，握手就被拒絕。這是「那台電腦」與「憑證」之間的問題，跟 Gitea 的帳號或倉庫權限無關；同一台電腦 clone 152 上任何倉庫都會遇到。
怎麼分辨不是權限問題
權限問題是 404 或 403（見 9.1），而且連得上之後才會出現。這個錯誤在 TLS 握手階段就失敗，還沒有走到 Gitea。
處理 A：只對這個倉庫關閉驗證（最快，每個倉庫都要做）
第一行的 -c 只對這一次指令生效，因為 clone 完成前還沒有倉庫可以設定；之後的 pull、push 靠第三行。
處理 B：讓這台電腦信任 152 的憑證（一次解決，尚未驗證）待辦
用 certutil -addstore -user Root server.crt 把 152 的 server.crt 匯入受信任根憑證，詳細步驟與可能遇到的後續錯誤見 9.3。
pyDMS 自己會處理（2026-11-25）
pyDMS 跑 git（自動更新、管理頁的更新按鈕、同事 repo 的下載與更新）遇到這個錯誤時，會只對那個 repo 寫入 --local http.sslVerify false 再試一次，不動 --global（PL-1125-GIT-1）。管理頁 Git 狀態的「憑證檢查」會顯示是不是關著。
錯誤後面那串亂碼是什麼
Windows 用 cp950 寫的中文說明：「憑證鏈結是由不受信任的授權單位發出的」。pyDMS 以前一律當成 UTF-8 來讀，所以變成亂碼；現在會正確顯示中文。亂碼本身不是另一個錯誤。
為什麼有這兩種選擇
見設計決策：git 對自簽憑證。
git：SSL certificate problem（其他環境的同類錯誤）

同樣是自簽憑證不被信任，只是不同的 git 後端用不同的錯誤訊息（Windows 的 schannel 是 SEC_E_UNTRUSTED_ROOT，見上一條）。只對這個 repo 關掉驗證：git config --local http.sslVerify false。不要加 --global。

git remote add origin 說 remote origin already exists

已經有 origin，改網址用 git remote set-url origin <新網址>。舊網址 http://…:3000/… 現在一定連不到。

我 push 了，但 152 上 git pull 拉不到新東西

先看你推到哪個 remote。開發電腦上 origin 是 GitHub，ntu_origin 才是 152 的 Gitea。用 git remote -v 確認，再 git push ntu_origin <分支>。另外確認 152 的工作副本所在的分支和你推的是同一個。

可以讓 git 只信任 152 的那一張憑證：git config --local http.sslCAInfo <server.crt 的路徑>。這是建議做法，尚未有人實際使用，細節與限制見 9.3。

在 152 的工作副本 git pull 不用輸入密碼，為什麼

「不可跳步」原則

  • 狀態檔：installer 用一個狀態檔（例如 state.json）記錄每個階段是否完成、檢查結果如何。狀態檔不含任何機密。
  • 開始前先驗前一階段：階段 N 開始前，重新驗證階段 N-1 的完成檢查；不通過就停，不往下做。
  • 可以重跑，不能跳：同一個階段可以重複執行，結果相同（冪等）；有唯讀的檢查模式。不提供跳到後面階段的選項。
  • 套件先驗證：manifest.json 固定每個套件的版本與 SHA-256，執行前比對，不符就停。
  • 範本不含機密：設定檔範本裡，.env 只列變數名稱；Gitea 的 secret 讓 Gitea 自己產生。

為什麼不給跳步。這套系統的失敗大多是順序造成的：後端還沒綁好 127.0.0.1 就開了防火牆、nginx 起來時後端不在而回 502、服務註冊時 .venv 還沒建好。手動做的時候靠人記順序；installer 把順序寫死，並且每一階段留下檢查紀錄，接手的人不必猜「上一個人做到哪裡」。代價是彈性變小：只想做其中一段的人，要用可獨立執行的動作（verify、backup-machine）或回到導覽手動做。

為什麼是「每樣東西各兩份」

  • 同一個倉庫、兩個 clone。測試的對象就是「即將變成正式版的那份程式」，所以來源必須是同一個倉庫，只差在切到哪個分支或標籤。用兩個獨立的 clone 而不是在同一個資料夾切換分支，是因為正式服務正在執行那個資料夾裡的檔案；切分支會直接換掉正在跑的程式。也不用「複製正式資料夾」來做：那會連 var\security.json、.env 和 .git\config 裡可能存在的權杖一起複製過去。
  • 兩個埠。同一個埠只能有一個程式在聽。8001 和 8000 一樣只綁 127.0.0.1，外面連不到，只有 nginx 進得來。
  • nginx 兩個 location，放在同一個 server 區塊。測試環境自動繼承 TLS、白名單與存取紀錄，不需要新的防火牆規則，也不會多一扇要守的門（單一入口的原則）。proxy_pass 和正式的寫法一樣，結尾不加斜線，由 pyDMS 自己認前綴。
  • 兩個 NSSM 服務。各自啟停、各自的 log、各自的重啟設定。測試服務當掉或被停掉，不影響正式服務。
  • 不同的 .env。埠與前綴本來就必須不同。.env 跟著資料夾走，兩邊各一份，才不會改測試設定時動到正式。
  • 不同的簽章密鑰。登入 cookie 是用這把密鑰簽的。兩邊同一把的話，在測試環境拿到的 cookie 可能在正式環境也被接受；測試環境跑的是還沒驗證的程式，不能讓它的登入狀態通到正式。
  • 測試用資料副本。測試的目的就是可以放心弄壞。資料來源預設是從備份還原一份到測試的 var，這也順便演練了還原。

下面每一條都是「預設決定（可改）」，寫法和第 4 章相同。

測試環境放在同一台機器、同一個 nginx 入口 預設決定（可改）

決策
在 152 上多跑一份 pyDMS，經由既有的 443 入口，以 /pydms-test/ 區分。
替代方案
另一台機器、同機 VM、只在開發電腦測試（第 12 章的方案 B 到 E）。
為什麼
改動最小：沿用白名單、憑證與管理方式，不新增對外埠。環境和正式最接近，「開發電腦能跑、正式不能跑」的機會最低。
代價
隔離只靠設定，不靠網路或機器；共用資源；152 壞了兩邊一起壞。

兩個獨立 clone，不共用資料夾 預設決定（可改）

決策
C:\pyDMS（master）與 C:\pyDMS_TEST（指定的分支或標籤），都從 DZLab/pyDMS clone。
替代方案
在同一個資料夾切換分支；用 git worktree；複製正式資料夾。
為什麼
各自的 .venv、.env、var、log 都跟著資料夾走，天然分開。切換分支不會動到正在執行的正式程式。
代價
多佔一份磁碟空間；兩邊各自要 pull 與安裝套件。

簽章密鑰與資料一律分開 預設決定（可改）

決策
測試的 .env 用另一把簽章密鑰；測試的 var 是副本，絕不指向正式資料庫。
替代方案
共用密鑰與資料，省去準備副本的工夫。
為什麼
測試環境跑未驗證的程式，它的登入狀態與寫入都不能通到正式。
代價
要準備並定期更新資料副本；副本裡的個資要另外考慮（見風險表）。

測試環境不更新正式環境 預設決定（可改）

決策
正式環境的更新只由正式環境自己的流程觸發。測試環境的內建更新功能只作用在測試分支。
替代方案
在測試驗證通過後，由測試環境自動把正式環境更新到同一版。
為什麼
自動化之前要先確定內建更新功能的實際行為，現在還不知道。
代價
上線多一個手動步驟。

動手前要先解決的事

  • 待確認cookie 的名稱與 path：需要在 pyDMS 的程式裡找 set_cookie 並讀相關程式（S10）。這一項沒有確認之前，兩個環境同時登入可能互相干擾。
  • 待確認pyDMS 內建 git 更新功能的行為：對哪個資料夾執行、用哪個 Windows 帳號（待辦第 27 項）。
  • 待確認var 的路徑是相對還是絕對。絕對路徑的話兩邊會共用同一份（S10）。
  • 待決定測試資料要不要匿名化；測試分支要不要保護、誰能合併（D16）。
  • 待辦先有備份。測試資料的來源就是備份（待辦第 20 項）。
  • 未實測整個方案還沒有在 152 上做過。
